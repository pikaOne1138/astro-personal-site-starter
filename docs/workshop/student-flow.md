# 學員建站流程與 AI 夥伴的角色

> 對象：維護這個研究展示 Repo 的人。**這份文件不會進學員 ZIP。** 學員與 AI 實際讀到的是 `docs/student-builder-pack/`、`docs/student-intake/` 與 `.ai/` 底下的 Skill。
>
> 這份文件取代了四份舊文件（AI 建站夥伴旅程、PR56 學員動線驗收、學員架站流程、三道品質關卡指南，已封存在 `docs/archive/`），保留的是設計準則與尚未驗證的 QA 清單。具體的頁面、步驟與數量以 `src/pages/`、`src/data/` 與頁面內容為準，不在這裡重複。

## 一句話

**學員說明想法並決定網站要呈現什麼；AI 幫忙訪談、規劃、設計、寫程式、預覽、排錯、上線和維護。網站與公開決定權屬於學員。** AI 是隨階段切換職責的**同一位建站夥伴**，學員不必理解或呼叫多個 Agent。

## 七個階段

| 階段 | AI 的角色與工作 | 學員要做的事 | 可交付成果 |
| --- | --- | --- | --- |
| 1. 需求訪談 | 需求顧問：逐步了解網站類型、目標讀者、想分享的知識或服務、訪客下一步。需求不清楚時先給具體例子，已清楚時不重複問 | 用自己的話介紹想法，不必準備完整規格 | 需求摘要、已確認與待確認資訊 |
| 2. 網站規劃 | 資訊架構師：決定內容優先順序、頁面、導覽、主要行動、Layout 與必要的 Blocks；可協助使用 `/starter/` 與 Site Brief | 確認哪些方向接近自己 | 網站地圖、Site Brief、設計決策 |
| 3. 網站設計 | Art Director／UI Designer：Layout → 編輯式構圖 → Blocks → 品牌與主題 → 適度動效；設計首頁、內頁與手機閱讀動線，不只是換配色 | 看範例，提出「像我／不像我」「太擠／太冷」等感受 | 視覺草稿、文案與版面方向 |
| 4. Astro 建置 | 工程師：用完整資料包、對應 Skill 與匯出器建立獨立 Astro 專案，整合文章或服務內容與響應式排版，執行 Build、查錯 | 必要時授權 AI 讀寫自己的專案 | 原始碼、可建置的網站、測試紀錄 |
| 5. 預覽與修改 | 驗收協助者加工程師：提供真正打得開且對應版本的 Preview，檢查功能、手機、鍵盤、內容，再依回饋修改 | 用手機或電腦看預覽，說想改哪裡 | Preview 網址、修改紀錄、驗收結果 |
| 6. 正式發布 | 發布協助者：說明公開後會看到哪些 DEMO、草稿、尚未設定的項目與風險，協助設定 GitHub Pages 或 Cloudflare，核對實際部署 | 明確決定是否照目前版本公開，並授權發布 | 正式網址、版本紀錄、未完成清單 |
| 7. 長期維護 | 網站維護助手：讀取學員自己的 Repo、`PROJECT.md`、既有設定與內容，更新文字、文章、服務、版型；先預覽、確認後再更新正式站，協助備份與復原 | 例如說「首頁這句幫我改掉」「新增一篇文章」 | 更新版本、Preview、發布與復原紀錄 |

## 誰決定什麼

AI 提供建議與技術操作；**學員決定**網站方向、對外內容、帳號授權與正式發布。AI 不會因為學員不懂程式就替他決定品牌、虛構資格或偷偷發布。

### 草稿也可以正式公開

Preview 可以含 DEMO、示範圖片、待補文字或尚未設定的聯絡方式。**正式發布前，AI 要指出它們在哪裡，問學員要保留、修改還是隱藏。** 學員明白公開效果並明確授權後，即使選擇照目前草稿原樣公開，AI 也應尊重，不擅自刪除，也不設內容完成度的硬門檻。

但密碼、Token、私人客戶資料不應因發布而外洩；不得把未驗證的證照、客戶見證、療效、付款或預約成功冒充真實。公開的 Preview 網址，知道網址的人都看得到，不要把敏感內容放進去。

### Preview 與正式上線不同

- **本機建置**：AI 已產生原始碼，Build 成功不代表外界看得到。
- **Preview**：真實網址可開啟，供測試與修改；要確認版本與內容。
- **Production**：學員已明確同意，AI 才進行獲授權的正式更新，並驗證正式網址。PR、Build 通過不等於 Production 已更新。

## AI 要具備什麼，才能真的建站

純聊天 AI 通常能協助訪談、構思與修改文案，但不一定有檔案工作空間、程式執行、GitHub 寫入或部署能力。能完成建置的環境，需要能處理完整 Astro 專案、執行 Build 與檢查；GitHub 與 Cloudflare 仍由學員建立或授權。學員可以先從手機做設計討論，再換到具備這些能力的環境建站。起始入口的「AI 能力確認」提示在 `docs/student-builder-pack/START-HERE.md`。

## 設計準則（之後修改引導、Starter、Skill、驗收時依循）

1. **先聽需求，再選 Layout。** 資訊架構先於裝飾；網站是多頁內容系統，首頁不是整個網站。
2. **已確認／AI 提案／待補／真實工具結果分開記錄**，不把學員尚未認可的提案寫成事實。
3. **降低初學者的決策負荷。** 一次處理一小步，給具體可比較的方向，不強迫每題都回答。
4. **保留人的內容與選擇。** DEMO 與非正式內容不等於不可公開；AI 提醒後由網站擁有者決定。技術 Bug 與內容未完成分開處理。
5. **使用已存在的元件與 Skill。** Layout、編輯式構圖、Blocks、Effects、Tokens 不混為一談；先查 registry，避免重複造輪子。
6. **真實 QA。** Build 成功不等於完成；至少看 1440／1280／768／390、鍵盤、觸控、內容、連結與手機閱讀動線，不只依賴模擬的視覺回饋。
7. **可接手、可維護。** 需求、來源、決策與網站狀態記在學員自己的 Repo 與 `PROJECT.md`；換 AI 後先讀現況，不重頭訪談。
8. **權限與發布可追溯。** 任何對外的 Git Push、PR、部署或 Merge 都依使用者明確授權的範圍；Preview 與正式站要核對對應的 commit。
9. **兩種網站類型優先**：知識／部落格、助人者／個人專業服務。不自行擴張成 CRM、會員、金流或預約後台。

## 學員的建站順序

給學員看的版本：**先選一個最接近你的整頁設計，再挑需要的局部段落，最後用 AI 換成自己的文字、圖片與品牌。** 不用先學會每顆元件的名稱。

1. 需求：網站寫給誰看、要提供什麼、訪客下一步做什麼。
2. 選網站類型與 Layout，記住 slug。**Layout 與品牌配色是兩件事**；規劃器提供的配色預設，不是對應的 Layout 數量。
3. 在 `/starter/` 規劃首頁、內頁、導覽與主要 CTA；沒有內容的頁面先不啟用。
4. 挑 Section Patterns（可跳過）：說清楚放在哪一頁、哪兩段之間。
5. 設定品牌視覺：從配色預設起步，調整五色；AI 要檢查顏色對比與手機閱讀。
6. 只在區段現有功能不夠用時，才去挑較細的 Blocks；最後才決定是否加入微動效，不要因為有範例就全部加。
7. 下載 Site Brief JSON，交給 AI 依 `astro-site-assembly` 組裝；透過 GitHub PR 預覽，實際檢查四個寬度。
8. 本人確認後才合併與部署。依序使用內容準備度、導覽測試、發布健康檢查三道關卡（見 `START-HERE.md`）；之後的文章、區段、還原走內容發布、部署、維護的 Skill。

補充：

- 學員要下載規劃器產生的 JSON，**不要自己照抄舊格式**（例如已不存在的 `sectionPatternSelections`）；AI 再依內容需求補上真實的作品或服務資料。全站 Footer 要避免重複組裝。
- 進階導覽的層數與各層上限，是規劃器程式裡的安全上限（見 `src/data/starter-config.ts` 與 `/starter/` 程式），不是建議學員塞滿。複雜的 mega-menu、第三層或圖片式選單屬於後續客製，不能假稱已支援。
- 發布前後要確認：正式網址、HTTPS、canonical、`robots.txt`、`sitemap.xml`，不可沿用 `example.com`；文章型網站要看列表、標題描述與搜尋索引是否真的建立；Search Console 是選配，提交 sitemap 不代表收錄。

## 學員的三種檔案

不要把它們編號成「第一、第二、第三份」，它們各有用途：

| 檔案 | 取得的地方 | 必要性 | 後續 |
| --- | --- | --- | --- |
| AI 需求訪談包 | `/starter/` 的訪談步驟 | 選填 | 解壓後交 AI 訪談；AI 整理摘要，學員貼回規劃器 |
| Site Brief JSON | `/starter/` 最後一步 | 建站交接用 | 保存網站設定（含貼入的訪談文字） |
| 完整建站包 ZIP | `/guide/` | 建站交接用 | 與 Site Brief 一起交給同一個具備專案操作能力的 AI，搭配正式提示詞 |

- 學員不必把訪談包重複交給建站 AI。
- 訪談摘要與規劃器設定若有實質矛盾，建站 AI 先問學員，不自行選擇優先權。
- Logo：AI 生成後學員下載，再上傳到規劃器；純文字的品牌方向貼進規劃器的訪談欄。
- 不做訪談、不上傳 Logo，仍應能建立 Site Brief 並開始建站。
- 「複製提示詞」是複製給 AI 的輸入，不是貼回規劃器；AI 的訪談結果才貼回規劃器。

## 教學驗收問題

- 學員能說出選擇 Layout 與 Section Pattern 的差別嗎？
- 能找到 Pattern 的展示，指出要哪一款、放在哪、怎麼替換內容嗎？
- AI 能維持原版型而增加 Pattern，不重複 Footer、不亂造新元件嗎？
- Build 與實際預覽都通過嗎？未配置的預約與法律頁面有沒有被誤當正式功能？

## 教學演練：復原

1. 先完成第一次發布並記錄正常的 commit。
2. 修改一段首頁文案 → 建立 PR → 確認預覽 → 合併發布。
3. 模擬改錯：另開 PR 還原那次修改，驗證結果，由學員同意後合併。
4. 假設換電腦：從 Repo clone、`npm install`、`npm run build`，核對圖片與文章。
5. 故障演練只在專用的測試 Repo 或分支做，不對正式網站故意破壞資料。

## 尚未驗證的學員旅程 QA

這份清單來自 PR 合併時的驗收項目，**沒有一項被記錄為已完成**。要驗證時註明日期、裝置、網址與結果；沒做過就維持 NOT TESTED。

- [ ] 首頁主路徑與資源路徑有明顯區隔，沒有只有標題的空 section。
- [ ] 前置準備頁只處理環境步驟，沒有殘留訪談包按鈕。
- [ ] 從 Layout 進入規劃器時，layout 與 kind 正確預選。
- [ ] 規劃器步驟連號，資源卡與按鈕在手機尺寸沒有溢出。
- [ ] 訪談包 ZIP 能解壓，文件完整且為 UTF-8。
- [ ] AI 訪談摘要可輸入多行，匯出的 Site Brief `notes` 保留文字與換行。
- [ ] 沒有訪談摘要時 Site Brief 仍能下載，且建站包接受該檔。
- [ ] Logo 與主視覺上傳、Site Brief 的 `assets` 保留正常。
- [ ] 規劃器最後一步到指南的錨點可用。
- [ ] 指南的完整建站 ZIP 實際能下載，內含預期目錄與檔案。
- [ ] 指南沒有重複的規劃器按鈕、設計顧問提示詞或額外的下載順序編號。
- [ ] 正式建站提示詞要求 AI 理解 Site Brief `notes` 並處理矛盾，且用建站包端到端驗證過。
- [ ] 桌面與手機瀏覽器 QA 通過。
