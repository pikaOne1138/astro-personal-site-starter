# 已上線網站健康檢查｜學員按需使用（唯讀）

> 這是既有 AI 網站夥伴的「健康檢查」任務，非另一套建站或維護入口。學員不必懂技術；可直接從 `/guide/` 複製下方內容。此檔不是排程監控，也不會啟用 GitHub Actions 或自動修復。
>
> 需有本次學員**自己的**網站網址；有權限才讀 GitHub／部署資料。AI 不得把網站開啟成功當成安全檢查通過，也不因為網站沒有提供原始碼就拒絕公開網站的檢查。來源規格仍以 ai-workbench 的 `projects/atp-starter/specs/astro-site-guardian.md` 為準。

## 可複製提示詞（從這裡開始）

我想知道**我自己已經上線的網站，現在是否正常運作、是否有最新的安全漏洞或重要版本更新、有哪些問題需要處理，以及目前是否需要維護**。

我沒有網站開發背景，不知道應該檢查哪些東西。請你**主動完成調查、判斷與整理**，不要先丟一大串技術問題給我，也不要要求我自己先了解 GitHub、套件版本或部署流程。

請遵守以下工作方式。

### A. 先找到並理解我的網站

1. **以我的網站為準。** 如果我提供網站網址，就先檢查這個公開網站；如果提供 GitHub 專案連結或你已能存取目前的網站程式，再讀取該專案。不預設你知道我的專案在哪裡，也不要把無關的專案拿來檢查。
2. 如果我沒有提供任何可辨識網站的資訊，**只問我一個簡單問題**：「可以給我你的網站網址嗎？」若沒有網址，也可以給專案連結。若網站已在目前對話清楚指定，不要重問。不要一開始就要求我填寫技術資料。
3. **有原始碼才檢查原始碼。** 能讀取專案時，先辨識實際使用的技術、套件與部署方式；再找有沒有網站說明、維護規範、版本鎖定檔、自動化檢查與部署紀錄。**不預設專案一定有任何特定名稱的文件、Skills 或自動化工具。** 沒有就如實說明，不要要求我先建立。
4. 只有公開網站而沒有程式或平台權限時，也先完成公開網站可以驗證的部分；涉及套件漏洞、GitHub Actions、版本與部署的項目則標明資料不足，不得推測。
5. 依網站實際用途和功能決定檢查範圍，不要假設每個網站都有文章、搜尋、預約或其他特定功能。

### B. 依實際情況自行檢查

請先自行制定適合本站的檢查範圍，然後使用當前可用的**唯讀工具**取得真實證據；能查的立即查，不要只列檢查計畫，也不要只根據檔名或提示詞推定已正常。不同檢查使用的證據各自獨立：公開網站、GitHub 原始碼、GitHub Actions／警示、部署平台與官方安全公告不可互相冒充。

- **訪客能否正常使用：**正式網址、HTTPS、首頁、主要內頁、導航、404、圖片、手機可用性；文章／分類／搜尋／RSS、服務／聯絡／預約／外部表單依本站功能決定是否檢查。能開啟網頁不等於每個互動都已測過。
- **內容與搜尋可見性：**真實頁面的標題、描述、Canonical、sitemap、robots、內部連結、是否仍有示範內容或無效連結；只檢查本站適用項目，不保證 Google 已收錄或排名。
- **網站維護、最新版本與漏洞：**若有原始碼，先從 `package.json`、lockfile、部署設定確認本站**實際使用**的 Node.js、Astro、整合套件與重要直接／間接依賴版本；不要只看 `package.json` 中允許的版本範圍。**主動上網查證截至本次檢查當天的最新資訊**，優先查官方 Release Notes／Changelog、GitHub Security Advisories、npm 套件公告、NVD（適用時），並交叉比對 GitHub Dependabot Alerts、既有更新 PR 及 `npm audit` 的可用結果。對每個可能影響本站的漏洞，確認公告日期、受影響版本範圍、本站實際版本、嚴重程度、修補版本與升級相容性；無法確認是否受影響時標記未確認，**不能只看到 CVE 或套件名稱就宣稱本站有漏洞**。對一般更新則查最新穩定版、發布日期、主要變更與是否有必要升級，分辨安全修補、Bug fix、一般功能更新及破壞性 Major 升級。**有新版本不等於有故障或必須立即升級**。若無法即時連網或無權讀取私有警示，明確說明資料查證截止點及缺口，不得用舊知識冒充最新消息，也不可擅自安裝套件或執行修補。
- **建置、部署與巡檢：**先辨識本站實際使用的 GitHub Pages、Cloudflare Pages 或其他平台，再核對可取得的建置紀錄、失敗訊息、部署紀錄與正式站是否已發布對應版本。若網站有既存的 GitHub Actions、Dependabot 或 Site Guardian，檢查設定是否存在、是否**真的啟用與按預期執行**、最近一次成功／失敗時間、是否有開放中的異常 Issue／更新 PR，並辨別問題是否已恢復；**有 YAML 設定不代表排程曾執行，單次檢查成功不代表長期監控穩定**。沒有安裝自動巡檢就如實說明，不要求學員事先安裝；不能把 Build 成功說成正式網站已驗證成功。
- **備份與復原：**查找已知正常版本、備份與恢復流程，確認備份是實際存在還是僅有書面說明；區分 GitHub 保存的原始碼和網域、外部表單、預約、電子報等不一定由 Git 保存的資料。不要求讀取或公開私人備份內容。
- **本站特有風險：**只針對網站實際使用的額外功能檢查。不要因為看見某個可能的風險，就自行擴大到不相關的資安測試；若涉及私人資料、授權或敏感路由，只使用安全、已授權的唯讀檢查，避免在報告公開敏感細節。

如果你不能連接 GitHub、讀取私人 Repository、取得部署平台資料、無法執行安全的掃描命令，或工具不支援某項檢查，**不要編造結果，也不要為了完成清單而要求我交出密碼、Token 或其他秘密**。先完成能查到的部分，再用白話告訴我還缺什麼權限、為什麼需要，並等我決定是否提供。

### C. 判斷問題是否值得處理

請區分：

- **需要優先處理：**有實際證據的網站故障、主要功能失效、明確影響本站的高風險安全問題。
- **可以安排維護：**有合理更新原因、相容性警訊、備份或維護流程缺口，但網站目前仍可使用。
- **目前不用處理：**只是有一般新版本、沒有證據顯示本站受影響，或只是偏好性改善。
- **尚無法確認：**缺少證據、權限或執行環境。明確區分 `NOT TESTED`（尚未測）與 `BLOCKED`（想測但被權限／環境阻擋）。

請根據實際證據判斷，不要把猜測寫成事實，也不要因為沒有查到問題，就宣布「完全安全」。有重大異常時先指出關鍵事實與影響，避免把一般小更新塞在最前面；若某項功能本來不存在或不適用，寫「不適用」而不是判 FAIL。對安全公告須說明它是否真的影響本站，若只是推測則明確標示。

### D. 用我聽得懂的方式交付

**請先給我一份白話摘要，而不是從技術報告開始。** 用繁體中文依序回答：

1. **網站目前怎麼樣？** 一兩段說清楚你真的確認了什麼、仍有哪些地方無法確認。
2. **我現在需要擔心什麼？** 最多先列三個最重要的問題；沒有重大問題就直接說，不必湊數。
3. **你建議我接下來做什麼？** 依「現在處理／下次維護／暫時不動」排列，簡單說明原因、影響與是否需要我決定。
4. **檢查依據與限制：**後面再提供給需要追查的人看的技術明細：每項適用檢查的 `PASS`／`FAIL`／`BLOCKED`／`NOT TESTED`、實際檢查時間、版本與漏洞公告的查證日期及官方來源連結、對應連結、Commit／Actions／部署證據（有查到才寫），以及未驗證原因。**不要捏造版本、日期、警示或證據連結。**

若你認為需要修復，請先用白話告訴我「準備改什麼、可能影響哪裡、不會動什麼、如何驗證」，**等我明確授權才開始動手**。

### E. 這次的權限邊界

這次**只讀取、分析、檢查與報告**。不要修改檔案、建立或修改 Issue／PR、安裝或升級套件、提交或 Push、合併、部署、變更 DNS、改網域、刪除內容或回滾；不要執行會改動網站、第三方服務或正式環境的測試。

請自行利用可用資源完成最多的調查；只有缺少真正必要的資訊或權限時才問我，並用非技術人能理解的說法解釋。公開網站檢查應避免會真的送出預約、付款、聯絡或訂閱的操作；若無法安全驗證，列為未測，不要創造假的成功紀錄。

> 注意：這份提示詞只指示 AI 唯讀檢查。若想安排自動每日／每週巡檢、異常 Issue 通知，屬於另一項 Site Guardian 安裝任務，不因使用此提示詞而自動具備。
