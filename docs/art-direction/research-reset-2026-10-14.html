研究結論：Subject Atlas 保留為有條件的主題型知識站候選；Practice Compass 暫不認定已具備充分的新增價值，需要把一般閱讀分流改為真正的服務選擇結構。這輪不新增第三套、不刪除既有程式、不改 #46、不做截圖驗收，也不標 Ready。

一、先把三個層次分清楚

工作坊的兩種用途是知識／部落格與助人者／個人專業服務。紙墨、晨光、靜室等是風格；田野筆記、長文書房、服務羅盤等是整站構圖。元件與動效則是實作材料。三者可組合，但換色、換字體或多一個 Adapter 都不能證明新增版型的價值。

新增方向必須回答：哪種學員的內容與需求，現有版型處理不好？內容是否容易準備與維護？拿掉顏色後，閱讀動線、首頁主角、內頁和互動是否仍不同？

五、Subject Atlas：保留，但修正適用條件

適用：有數個持續寫作主題、希望讀者跨日期找到內容的作者。不是所有剛開始寫三篇文章的人都需要一個知識庫。

案例依據：Ness Labs 與報導者支持主題／問題入口；Maggie 支持內容形式分流；閱讀前哨站支持作者、範圍與文章的連結。這些支持資訊組織，沒有直接支持目前 3:1 Hero、160px rail 或 64px 主題字級。後者是我們自己的設計選擇。

與 Curator 的差異：Curator 展示外部書籍、工具或收藏的策選；Atlas 組織站長自己的文章，主題詳細頁應有範圍說明、建議起讀文章與更多文章。與 Field Notes 的差異是問題分類先於日期；與 Reading Atlas 的差異是跨年度知識先於月份紀錄。

下一版 brief

  1. 定位與作者一句話 → 主題入口 → 一篇起讀文章 → 作者／寫作方式 → RSS／真實訂閱或文章索引。
  2. 主題只有一個或內容不足時，改呈現文章清單；不讓空分類占滿首頁。
  3. 首頁每主題只選少量入口；完整清單放主題頁。不要將全篇標題展開到首頁，再重复放最新文章。
  4. 主題資料需 title、slug、description、可選 startArticle；文章有 topics、title、description、日期。新增欄位尚未實作。
  5. 桌面侧索引服务跨主題跳轉；手機改自然流中的主題連結。主題與文章內頁保留同一編目語彙。

判定：用途缺口成立，構圖仍需少內容／長內容測試與後續視覺驗收；不稱為最好或唯一方案。

六、Practice Compass：目前證據不足，先重整

現況問題：首頁固定三列「是否適合／合作怎麼進行／還不想聯絡」，連到範圍、服務、FAQ。這只是閱讀準備程度的導航，不是依具體服務做選擇。與 Trust Path 同樣圍繞範圍、流程、揭露與低壓聯絡；「改用三列」不足以證明值得增加一套。

案例依據：Orka 真正按需求找不同服務／專業者；Mel Noakes 有不同方案入口；Kristin 與 Therapi 則示範具體本人、對象、方法和 FAQ。借用的是選擇與身份資訊，不移植團隊媒合、測驗或預約後端。

下一版 brief：讓羅盤真的協助選擇

  1. 服務者／服務對象定位 → 1–3 個真實服務入口 → 方法與本人 → 同欄比較形式／時間／費用／界線 → 初次合作流程 → FAQ／詢問。
  2. 每個入口對應服務對象、安排及詳頁，而非泛用的「了解更多」。只有一项服務时，直接展示該項服務，不硬湊三條。
  3. 新增方向以 service choices 為主要資訊物件；Trust Path 保留單一合作的循序五站；Clinician 保留專業範圍／資格查核為主。
  4. 資料需 services[]（slug、name、audience、summary、format、duration、feeNote、scope、nextStep）与本人介紹。現有 serviceInfo 字串表無法支撐完整方案選擇；這是待重整項，不能聲稱已完成。
  5. 桌面用可比對服務條目与對照表；手機每項依同一欄位順序堆疊。若無法做出實際選擇差異，保留作 Trust Path 的局部構圖，不繼續擴充為獨立模板。

判定：保留既有程式作候選，暫不認定設計擴充已成立。沒有直接刪除或替換這輪的已授權 Adapter。

七、目前程式與宣稱的差距

  • Definitions 的 contentKey 還有 topicEntries、latestNote、visitorIntents 等原型概念；目前 Adapter 的資料入口是 artDirection.topics、Content Collections、scope／serviceInfo／faq，且三種訪客入口固定在程式內。需要統一契約。
  • 兩個 Home 都直接指定 Arial／Georgia 等字體，會影響共用層的 typography preset 生效。品牌字體可調性不能只看設定欄位存在。
  • 兩套首頁缺少獨立的作者／服務者短介。About 頁與導航存在，不等於首頁已建立身份與信任。
  • Atlas 首頁每類展開全部文章，資料量大時會變成冗長索引。原型八個標題的畫面不能代表真實文章庫。
  • Practice 固定入口與單一揭露表不足以呈現多項服務的差異；應先做內容模型与對应內頁，再談「服務選擇」設計完成。

八、PR #47 的收斂順序與 #46 交接

  1. 先以本研究重新定位两個方向，停止新增版型、Generator 与額外 UI。
  2. 下一個開發批次先修資料契約、字體設定与本人短介，再處理 Atlas 資料量和 Practice 真實服務選擇。此研究提交不提前修改 renderer。
  3. 沿用 #46 的 templates → starter → guide → 既有 AI 建站資料包與單一開始提示。CLI 是 AI 内部工具，不能要求零基礎學員改走終端機操作。
  4. #46 接手既有 Gallery／Planner／主 exporter；#47 提供 renderer、欄位、fallback、required pages 与 in-progress 狀態。新增獨立 CLI 在整合後應收斂，避免長期兩條產品流程。
  5. 真實內容、文章／服務連結与建置检查可继续；本輪截圖驗收延期。沒有四寬度證據，不給視覺 PASS、不稱 ready。
