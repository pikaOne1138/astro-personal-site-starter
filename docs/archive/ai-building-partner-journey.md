# ATP｜AI 建站夥伴的角色與完整流程

> 適用對象：第一次建立個人網站、沒有程式經驗的學員。這也是 ATP 日後改善引導、Starter、AI Skills、驗收流程時的共同設計準則。
>
> ATP 的目標是幫你擁有一個可以自己更新的 Astro 網站，而不是讓你先學會寫程式。AI 是會隨階段切換工作職責的**同一位建站夥伴**，不必理解或自行呼叫六個獨立 Agent。

## 一句話說明

**你說明想法並決定網站要呈現什麼；AI 幫忙訪談、規劃、設計、寫程式、預覽、排錯、上線和維護。網站和公開決定權屬於你。**

## 七個階段

| 階段 | AI 的角色與工作 | 學員需要做的事 | 本階段可交付成果 |
| --- | --- | --- | --- |
| 1. 需求訪談 | **需求顧問**：逐步了解你的網站類型、目標讀者、想分享的知識或服務、訪客下一步。需求不清楚時先給具體例子；已清楚時不重複詢問。 | 用自己的話介紹想法；不必準備完整網站規格。 | 需求摘要、已確認與待確認資訊 |
| 2. 網站規劃 | **資訊架構師**：決定內容優先順序、頁面、導航、主要行動、Layout 與必要的 Blocks；可協助使用 /starter/ 與 Site Brief。 | 確認哪些方向接近自己。 | 網站地圖、Site Brief、設計決策 |
| 3. 網站設計 | **Art Director / UI Designer**：Layout → Editorial Composition → Blocks → Brand/Theme → 適度 Motion；設計首頁、內頁與手機閱讀動線，而不只是換配色。 | 看範例、提出「像我／不像我」「太擠／太冷」等感受。 | 視覺草稿、文案與版面方向 |
| 4. Astro 建置 | **工程師**：使用完整資料包、對應 Skills 與 Exporter 建立獨立 Astro 專案，整合文章或服務內容、響應式排版，執行 Build、查錯。 | 在必要時授權 AI 讀寫自己的專案；不必自己寫程式。 | 專案原始碼、可建置網站、測試紀錄 |
| 5. 預覽與修改 | **驗收協助者＋工程師**：提供可真正打開且對應版本的 Preview，檢查功能、手機、鍵盤、內容，再依你的截圖和自然語言回饋修改。 | 用手機或電腦看預覽，告訴 AI 想改哪裡。 | Preview 網址、修改紀錄、驗收結果 |
| 6. 正式發布 | **發布協助者**：說明網站公開後會看到哪些 DEMO、草稿、尚未設定項目與可能的風險，協助設定 GitHub Pages 或 Cloudflare；核對實際部署。 | 明確決定是否照目前版本公開，授權發布。 | 正式網址、版本紀錄、未完成清單 |
| 7. 長期維護 | **網站維護助手**：讀取自己的 Repo、PROJECT.md、既有設定與內容，更新文字、文章、服務、版型；先預覽、確認後再更新正式站，協助備份及復原。 | 例如說「首頁這句幫我改掉」或「新增一篇文章」。 | 更新版本、Preview、發布與復原紀錄 |

### 哪些事情由你決定？

AI 提供建議與技術操作，你決定網站方向、對外內容、帳號授權與正式發布。AI 不會因為你不懂程式就替你決定品牌、虛構資格或偷偷發布。

### 草稿也可以正式公開

Preview 可以包含 DEMO、示範圖片、待補文字或尚未設定的聯絡方式。**正式發布前，AI 應指明它們在哪裡，問你要保留、修改還是隱藏。** 即使你選擇照目前草稿原樣公開，只要明白公開效果並明確授權，AI 就應尊重你的決定；不應擅自刪除或設內容完成度的硬門檻。

但密碼、Token、私人客戶資料不應因發布而外洩；不得把未驗證的證照、客戶見證、療效、付款或預約成功冒充真實。公開 Preview 網址也可能被知道網址的人看到，請不要把敏感內容放進去。

### 「Preview」與「正式上線」不同

- **草稿／本機建置**：AI 已產生原始碼，Build 成功不代表外界可以看。
- **Preview**：真實網址可開啟，供你測試與修改；需確認版本與內容。
- **Production**：你已明確同意發布，AI 才進行獲授權的正式更新，並驗證正式網址。PR、Build 通過不等於 Production 已更新。

## AI 要能做到什麼，才能真的建站？

純聊天 AI 通常可協助訪談、構思與修改文案，但不一定有檔案工作空間、程式執行、GitHub 寫入或部署能力。能完成建置的 AI 工作環境需要能處理完整 Astro 專案、執行 Build 與檢查；GitHub／Cloudflare 仍需由你建立或授權。你可以先從手機做設計討論，再使用有必要能力的 AI 環境進入建站，是否能全程只用手機取決於所選工具。

## ATP 團隊後續修改依循的原則

1. **先聽需求，再選 Layout**：資訊架構先於裝飾。網站是多頁內容系統；首頁不是整棟網站。
2. **已確認／AI 提案／待補／真實工具結果分開記錄**：不得把學員尚未認可的提案寫成事實。
3. **對初學者降低決策負荷**：一次處理一小步，給具體可比較的方向；依學員清晰度調整，不強迫每題回答。
4. **保留人的內容與選擇**：DEMO 和非正式內容不等於不可公開；AI 提醒後交由網站擁有者決定。技術 Bug 與內容未完成要分開處理。
5. **使用已存在的元件與 Skills**：Layout、Editorial Composition、Blocks、Effects、Tokens 不混為一談；先查 Registry，避免重複造輪子。
6. **真實 QA**：Build 成功不等於完成；至少檢查 1440／1280／768／390，鍵盤、觸控、內容、連結與手機閱讀動線。不能只依賴模擬的視覺回饋。
7. **可接手與可維護**：把需求、來源、決策及網站狀態記在學員自己的 Repo／PROJECT.md；換 AI 後先讀現況而非重頭訪談。
8. **權限與發布可追溯**：任何對外 Git Push、PR、部署或 Merge 都要依使用者的明確授權範圍；Preview 及正式站要核對對應的 Commit，不假稱已完成。
9. **兩種網站類型優先**：知識／部落格與助人者／個人專業服務。不自行擴張為 CRM、會員、金流或預約後台。

### 給學員的最簡單使用方式

你不必一次做完七個階段。可以先對 AI 說「我想有自己的網站，但還不知道要做什麼」，請它一次問一個問題；當你說「先做給我看」，AI 應協助建立可預覽的草稿；當你說「這樣可以公開」，AI 應先說明現況並取得你的正式發布確認。三週後想修改，就回到自己的網站專案請 AI 接手。
