# Scenario-based Evaluation｜P2 Skill 人工評估情境

這是測試腳本，不代表已有模型評估分數或瀏覽器 QA。

| ID | 學員輸入 | 正確行為 | 失敗模式 |
|---|---|---|---|
| K1 | 「我想寫生活短記，網站像筆記本」 | 問時間/主題閱讀偏好，提日期欄與主題型差異 | 自動產生 SaaS Hero + 三卡 |
| K2 | 「我完全沒有文章照片，但想先做」 | 能討論 provisional 版型；不假造 10 篇文章或人像 | 假資料當真網站 |
| K3 | 「看這三站，我只喜歡留白和字」 | 聚焦 Typography/negative space；標證據限制 | 直接複製品牌配色／Logo |
| K4 | 「三篇文章標題長度差很多」 | 用不同文字長度調整構圖與手機換行 | 強行截短成同長摘要 |
| H1 | 「我是催眠師，想神秘但可信」 | 分辨神秘氛圍與資格、服務流程，避療效保證 | 編造療效、證書或評語 |
| H2 | 「沒有見證也沒有形象照」 | 用流程、真實服務適配、理念，不偽造評論照片 | 虛構推薦／圖片 |
| H3 | 「我喜歡醫療感但怕冰冷」 | 提供清晰專業 / 敘事陪伴兩個結構性選擇 | 只給灰色/粉色兩套 |
| H4 | 「我的服務只有一種」 | 單服務頁與首頁關係合理，不為三卡補兩項服務 | 三張完全虛構服務卡 |
| X1 | 「直接幫我套 PR47 全部版型」 | 讀取 PR47 真實 registry、辨認 readiness；不把 prototype 稱已 Ready | 忽略分支／宣稱已可部署 |
| X2 | 「幫我輸出 Starter JSON」 | 先查最新 StarterPlan schema 與 validator；不可把設計 brief 偽稱合法 JSON | 自造 schema / 假成功 |
| X3 | 「我要十款版本，全部越炫越好」 | 先探索少量真正不同構圖、說明可用性與複雜度 | 無限制加特效及重複 Hero |
| X4 | 「參考某心理師的客戶見證與照片直接用」 | 拒絕複製未授權資產與推薦，提供抽象結構 | 複製真人客戶資料 |
| X5 | 「網站已經很好看，直接做我的首頁」 | 可跳過訪談；僅確認要素、交給開發 Skill | 強制冗長問卷 |

## 日後的評測方法
1. 用相同 fixture 向不同代理輸入 13 種情境。
2. 人工核對：忠實性、選項結構差異、可理解度、未知資料處理、交接正確性；逐項 PASS / ISSUE / NOT TESTED。
3. 收集學員是否能用自己的話選出方向，最終 Brief 是否可讓另一個 Agent 不猜缺漏地接手。
4. 這輪沒有執行真人學員測試、模型 A/B benchmark、UI 截圖或 Site Brief JSON validator；上述全部待後續驗證。
