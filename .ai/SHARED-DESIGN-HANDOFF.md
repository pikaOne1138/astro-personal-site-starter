# 跨 Skill 設計決策交接契約

本文件是各設計類 Skill 在學生 ZIP 中可獨立閱讀的共用判斷契約，不建立新 Skill、不修改版型。

## 分工
- Design Consultation：釐清意圖、真實資料、設計方向、取捨、否定選項；整理 Design Brief。
- Layout Craft：整頁資訊架構、閱讀順序、首頁與內頁結構、手機重排。
- Editorial Layout Design：Hero、區段構圖、列表、留白與節奏。
- Section Pattern Craft：使用 Registry 內的可重用 Section Pattern，不憑空創造資料。
- UI Craft：元件、Tokens、一致性與操作可用性。
- Motion Craft：有目的的 subtle 動效、降級與無障礙。

## 每次階段交接最小資訊
1. 網站類型、受眾、訪客首要任務。
2. 已確認的 Product Truth 與資料來源；missing 保持 missing。
3. 學員已確認的 Layout / Section 順序 / 手機順序，未核對 ID 標 not-verified。
4. 被否決的結構與明確理由，不得下游又塞回來。
5. 設計假說、採用理由、代價及尚未決定項目。
6. 待測試項目與證據；Build PASS 不等於視覺 PASS。

## 驗收情境（只檢查規則與輸入輸出契約，不冒稱已跑真模型）
- A 同內容、同色字，不同 Layout：各 Skill 都保留首頁、內頁、手機閱讀動線差異，不將換皮當新設計。
- B 無照片／見證／證照：不產生空白破版、虛構成果、假 CTA 或尚未設定的可用服務。
- C 否定大圖 Hero：下游不得重新加入大圖 Hero，即使改顏色與動畫也不算修正。

## 學生包可攜性
以 `scripts/build-student-pack.mjs` 的 ZIP 清單確認共用規則及 .ai/ Skills 均可讀。純聊天工具無法讀取檔案時不能聲稱已使用 Skill。

## 不依賴研究原文的共同原則
- **Structure before decoration**：先受眾、訪客任務、內容和網站結構，再處理字體、配色與動效。
- **Content shapes composition**：用真實文章長短、實際服務數量和無圖情境決定版面；不要為了卡片裁切真實標題。
- **Layout ≠ Theme**：不同 Layout 必須在資訊順序、Hero／欄位／內頁或手機重排至少幾個面向有真正差別；換色不是新 Layout。
- **Evidence hierarchy**：分清學生確認的事實、直接觀察、推論、AI 提案和缺資料；缺少資格、價格、見證、照片、聯絡端點時不得編造或顯示假成功。
- **Respect rejection**：已否定的版面模式保留否定理由，下游不得換皮引入；若有可用性危險要解釋並重新確認。
- **Responsive/accessibility**：手機閱讀順序、鍵盤、可讀性、reduced-motion 要事先規劃；沒有實際檢查就標記 NOT TESTED。
- **Stop condition**：有足夠決策資訊後應轉入實作與預覽，不要無限提出新方案；技術測試通過不等於主觀視覺已驗收。

## 避免罐頭構圖
- 每個主頁先定一個主焦點與閱讀路徑，優先比較「不靠換皮仍辨識的結構」。
- 不預設「置中標語 + 雙 CTA + 三個等寬 icon 卡」。內容客觀上剛好三項時三欄可以成立；禁止的是沒有理由的預設。反過來，也不是一律改成不對稱：高度規整對稱的頁面，要能說明為什麼適合這個內容與使用情境。
- 內容長度驅動版面：真實標題長短不一、內文自然長度，決定 Hero 寬度、標題斷行、圖片比例與清單樣式。不要為了整齊裁掉重要資訊，也不要為了湊整齊塞入等長的假內容。
- 同一品牌的 About、文章內頁、服務內頁必須繼承首頁的視覺語言，但可以依任務調整資訊密度與版面。
- 至少測這幾種情境：空內容、單篇／單項服務、長中文標題、無圖與有圖；無圖時也要有可辨識的構圖。

## 設計批評的格式
批評必須可執行，每個議題依序寫出：**觀察證據 → 訪客後果 → 原因假說 → 最小修改 → 如何驗證**。

- 不要只說「缺乏設計感」「再高級一點」，也不要只給空泛的分數。
- 「技術可測」與「人工視覺」分成兩份結論；沒測過就標 `not-tested`，不能填 PASS。可用的標記只有 `not-tested`、`issue`、`pass-with-evidence`。
- 審查紀錄要寫明截圖路徑、視窗寬度、git SHA、使用的 fixture 與日期。

## 設計審查面向
這張表不產生美學總分，也不採用第三方自評的分數當客觀證據。

| 面向 | 判斷問題 | 測試方法 | 阻塞級 |
|---|---|---|---|
| 目標／資訊架構 | 進站是否知道這裡寫什麼、幫誰、下一步是什麼 | 閱讀首屏與導覽，兩類客群各自的任務 | 高 |
| 結構差異 | 同內容同主題下，還能分出不同版型嗎 | 用同一份中性 fixture 並排，逐項比 Hero、列表、內頁、手機動線 | 高（版型庫） |
| 視覺階層 | 第一視覺焦點與次要訊息清楚嗎 | 1440／1280／768／390 截圖人工審閱 | 高 |
| 內容優先 | 一項服務、三篇文章、很長的標題，不靠假資料也成立嗎 | 空、稀疏、長中文、缺圖的 fixture | 高 |
| 真實信任 | 資格、評語、價格、聯絡、外部預約都有事實依據嗎 | 核對欄位來源與實際連結 | 阻塞 |
| CJK 與影像 | 中文換行、段距、圖片主體與裁切合理嗎 | 四個寬度的視覺回歸 | 中高 |
| CTA 與導覽 | 主要行動與低壓力入口清楚，訪客能返回嗎 | 鍵盤、觸控、無 JS 的功能檢查 | 高 |
| 可及性 | 對比、焦點、觸控目標、縮放、reduced-motion 合理嗎 | 靜態檢查加 axe 加人工鍵盤與讀屏 | 阻塞（嚴重問題） |
| 技術品質 | build、`BASE_URL`、Pagefind、截斷、CSS 依賴 | CI 加實際 Preview 驗證 | 高 |
| 品牌一致 | 是否只換了顏色，而首頁與內頁像兩個站 | 跨頁人工設計批評 | 中高 |
