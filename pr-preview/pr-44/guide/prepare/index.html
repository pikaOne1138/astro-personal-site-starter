PREPARATION / 完全不會程式也能照做

先準備好，再開始建置。

建立 GitHub 帳號、連接 AI、準備網站內容與品牌圖片。

註冊 GitHub 帳號 ↓註冊並登入 GitHub。建立自己的倉庫 ↓建立網站倉庫。連接 AI 與 GitHub ↓新帳號首次授權，分清唯讀與寫入。網站內容訪談 ↓下載訪談包，與 AI 討論內容。Logo、Favicon 與網站圖片 ↓用 AI 設計 Logo、favicon 和圖片。選擇發布方式 ↓A｜GitHub Pages 或 B｜Cloudflare Pages。

01｜註冊並登入 GitHub

  1. 開啟 GitHub 註冊 ↗；若已有帳號，就直接登入。
  2. 登入後，確認右上角頭像選單能看到自己的帳號名稱。
  3. 記下自己的 GitHub 帳號名稱。
找不到按鈕？截圖給 AI，請它教下一步。截圖前遮住敏感資訊。

02｜建立網站倉庫

  1. 開啟 GitHub New repository ↗。
  2. 確認 Owner 是自己的帳號。
  3. Repository name 輸入英文簡短名稱，例如 my-personal-site。
  4. 選擇倉庫公開方式：建議初學者選 Public（公開），設定最簡單，但原始碼也會公開。 若選 Private（私人），後續建議使用 Cloudflare Pages；其他方案詳見 第 06 步｜選擇網站發布方式。
  5. 勾選 Add a README file，其餘保持預設。
  6. 點 Create repository。看到 你的帳號/my-personal-site 的 Code 頁，代表倉庫建立成功。

不會操作？複製提示詞給 AI。

請一步一步教我在 GitHub 建立個人網站倉庫。每次只給一個步驟，告訴我要按哪裡、成功後會看到什麼。如果介面不同，請我截圖給你確認。不要要求密碼或驗證碼。

03｜第一次連接 AI 與 GitHub：要能讀，也要能修改

這一步是讓 AI 能在你自己的 GitHub 倉庫建立網站。第一次使用全新帳號時，單純「連接成功」不等於 AI 已有寫入權限。以下以 ChatGPT Codex Connector 為例，其他 AI 的介面與權限名稱可能不同。

第一關｜在 AI 端連接 GitHub

  1. 登入你準備用來建站的 AI 工具，找到設定／連接應用程式（Connections／Plugins 或同等項目），連接 GitHub；依服務介面完成 GitHub 授權。
  2. 確認目前使用的 AI 模式具備編輯專案、寫入 GitHub 和建立 PR 的能力。只有「搜尋檔案／讀取倉庫」的連線，可能無法完成建站。
  3. 若授權畫面將 Read-only（唯讀）與 Write／Edit（可寫）分開顯示，不要只看「已連線」；由 AI 回報它目前實際能使用的操作。

安全原則：不要貼密碼、Token 或驗證碼到聊天視窗；不要因為找不到寫入功能就直接開放所有 Repository。

第二關｜在 GitHub 限定可存取的倉庫

  1. 開啟 GitHub 已安裝的應用程式 ↗，找到這次使用的 App（例如 ChatGPT Codex Connector），按 Configure。
  2. 找到 Repository access，建議選 Only select repositories（僅指定倉庫），不要選 All repositories。
  3. 在 Select repositories 選剛剛建立的網站 Repo，按 Save。新建的倉庫不一定會自動加入原本的選取清單。
  4. 若畫面顯示 App 的權限是唯讀、而 AI 需要修改 Repo，請先回 AI 工具檢查可寫入的連線／工作模式；僅變更 Repository access 清單不能把唯讀 App 升級成寫入 App。

第三關｜請 AI 做能力確認（先不要正式修改）

將這段話貼給 AI，再依它的實際結果決定下一步：

請透過我已授權的 GitHub 連線，確認你能否讀取我的網站倉庫 README、建立 Feature Branch、提交新檔案、建立 Pull Request 與讀取 Actions 結果。請分別回答「能做到／只有唯讀／需要進一步授權／目前無法確認」，不要因為看得到 README 就說已經能寫入。先不要修改 main、Merge 或部署。

第一次操作真的建立 Branch／PR 時，AI 應先使用明確的測試分支，並得到你對該倉庫的授權。

排錯：AI 看得到 Repository 卻不能寫，先查工具模式和 App 權限；AI 找不到新 Repo，先回 GitHub Installed Apps 檢查 Only select repositories 是否已加入並儲存。若授權按鈕與教學不同，請截圖給 AI，不要猜。

05｜不用事先有 Logo：一起做品牌圖像

  1. 從三款概念選一款。
  2. 確認 Logo 中文名稱正確。
  3. 請 AI 檢查 favicon 在小尺寸是否清楚。
  4. 確認圖片沒有冒充真實人物、客戶或場所。

06｜選擇網站發布方式

請先選擇 A 或 B點選下方卡片，查看對應設定步驟。

可以先選 Public（公開）完成建站，日後接好 Cloudflare Pages、確認部署正常，再將 GitHub 倉庫改成 Private（私人）。 免費 GitHub Pages 需要公開倉庫；想用私人倉庫搭配 GitHub Pages，須符合付費方案資格。Cloudflare Pages 支援私人倉庫，網站仍可公開瀏覽。

A｜GitHub Pages：設定步驟

GitHub Pages 連接網站：照著操作

  1. 開啟 GitHub 我的倉庫清單 ↗，找到這次建立的網站倉庫並點進去。也可以在 GitHub 頁面右上角點 All repositories（倉庫圖示），從清單開啟。
  2. 點選上方 Settings。
  3. 從左側選單點 Pages。
  4. 找到 Build and deployment → Source，選擇 GitHub Actions。
  5. 請 AI 在你自己的 PR 執行唯讀建置檢查。Build 成功、下載 Artifact 都不是可直接打開的網站預覽。請 AI 先安排獨立 Preview（例如另一個僅供驗收的 Cloudflare Pages 專案／分支），提供真正可打開的測試 URL 並確認 Commit SHA。
  6. 看到測試網址後先檢查首頁、內頁、圖片與手機版，確認內容無誤才允許 AI Merge。完成確認後，再由你本人或經你授權的 AI 在 GitHub Actions 手動執行正式發布 workflow；不要把 Build 綠燈當成已發布。
  7. 正式發布 workflow 成功後，才到 Settings → Pages 按 Visit site 檢查正式網站；首次發布前可能尚無此按鈕。

分開確認：驗收階段需有真正可打開、與正式站隔離且對應當次 Commit 的 Preview；經你明確同意後，才確認正式站顯示 Your site is live at ...。GitHub Pages 不會憑 PR Build 自動提供獨立預覽網址。

如果畫面與教學不同，截圖給 AI，請它依畫面指引。

B｜Cloudflare Pages：設定步驟

Cloudflare Pages 連接 GitHub：照著操作

  1. 登入 Cloudflare，左側選 Workers 和 Pages，點右上角 建立應用程式。
  2. 在「建立新項目」頁面，不要選「從 Hello World 開始」。點畫面下方的 「前往 Pages」，切換到 Pages 建站流程。
  3. 在 Pages 選 連接至 Git／Connect to Git，再選 Continue with GitHub。
  4. 若是第一次使用 Cloudflare，可以先在右上角帳號選單尋找語言設定，將介面切換成自己容易閱讀的語言；不同帳號介面可能不同，找不到可略過。
  5. 若跳出 GitHub 授權畫面，依指示連接 Cloudflare Workers and Pages App。這是 Cloudflare 與 GitHub 的另一段授權，和第 03 步 AI／Codex 的 GitHub 授權不同。 AI 能看到倉庫，不代表 Cloudflare 一定能看到。
  6. 打開 GitHub Applications，找到 Cloudflare Workers and Pages → Configure。在 Repository access 選 Only select repositories，加入你的網站倉庫並按 Save。
  7. 回到 Cloudflare 的 GitHub 倉庫選擇畫面，重新整理或重新開啟連線，確認自己的新 Repo 確實出現在清單；沒有出現就先別猜 Repo 名稱或改用老師的倉庫。
  8. 回到 Cloudflare，從清單選自己的網站倉庫，進入「設定組建和部署」。
  9. 先確認首次公開行為：Cloudflare 的 Save and Deploy 會進行首次正式部署，即使網址暫時只是 pages.dev。若還未確認內容，請 AI 先建立不含個人資料的測試站／測試分支，使用獨立的 preview 專案及 Git Preview Deployments 取得測試 URL；不可直接把未確認的 main 當正式站發布。
  10. 部署前核對以下設定。
    確認與下列設定一致，再按部署
    生產分支
    main
    Framework preset
    Astro
    組建命令
    npm run build
    組建輸出目錄
    dist

    通常會自動帶入。若顯示不同，先請 AI 協助確認；專案名稱可自行決定。

  11. 只有在你理解這是首次公開部署、已檢查測試 Preview 並明確允許時，才點 儲存並部署／Save and Deploy。請 AI 核對測試分支 Preview URL、Commit SHA、資產與導航。正式 main 公開前再次徵求你同意。

分開確認：Preview Deployment 是驗收環境；Production（包含首次 Save and Deploy）是公開環境。兩者均應顯示實際對應 Commit。缺少 Preview 或無法隔離正式站時，不要宣稱學員已完成安全的「先預覽後發布」。

畫面若出現「部署命令 npx wrangler deploy／預覽命令 npx wrangler preview」等 Workers 設定，表示可能進到 Workers 流程。請返回選 Pages，不要照 Workers 欄位繼續設定。若選不到倉庫，回 GitHub 的 Cloudflare Workers and Pages App（不是 Codex Connector）檢查 Repository access，加入後再重新整理 Cloudflare。

Cloudflare Pages 有什麼好處？哪些 GitHub Pages 也做得到？

GitHub Pages 與 Cloudflare Pages 都能發布網站。

比較項目Cloudflare PagesGitHub Pages
私有 Repo 部署公開網站支援，原始碼可維持 Private。免費個人方案不支援私有 Repo 發布 Pages；公開 Repo 可用。Pro／Team 等適用方案另有支援。
自動更新網站Git 整合推送後自動部署。有。使用 GitHub Actions 或 GitHub Pages 發布來源。
PR／分支預覽Git 整合提供獨立預覽網址。可做到，但通常要自行配置預覽 Workflow 或其他服務，並非一般 Pages 預設功能。
自訂網域與 HTTPS支援 pages.dev 預設網址、HTTPS 和自訂網域。有。提供 github.io 預設網址、HTTPS 和自訂網域；兩者網域購買費用另計。
限制預覽觀看可另啟用 Cloudflare Access 保護 Preview。一般 Pages 無同等一鍵功能。企業方案有特定私有發布能力，但不等於一般 PR 預覽保護。
網站流量分析可選用 Web Analytics。可另行加入 Google Analytics 或其他分析工具；GitHub Pages 無同等內建訪客分析面板。
網址轉址／HTTP 標頭可用 Pages 的 _redirects 與 _headers 規則。部分可做到。網站可生成跳轉頁、設定其他服務，但 GitHub Pages 不直接提供等同的伺服器端規則功能。
指定頁面／路徑存取控制可另外配置 Cloudflare Access 或規則；不是自動的。一般免費 Pages 不提供按路徑的登入控管。企業私有 Pages 為不同使用場景。

選擇建議：公開原始碼可用 GitHub Pages；希望原始碼保留私人，選 Cloudflare Pages。私人倉庫不代表網站不公開。
